# Проект 1: inknet-hybrid (Вариант B)

**Гибридная строчная модель: растровая CNN + векторная ветка штрихов, общий CTC-декодер.**

- Статус: план, не начат
- Зависимости: веб-клиент (сбор написаний), `../inknet-train`
- Владелец модели: `../inknet-train`; инференс-слой: веб-клиент

## 1. Идея и мотивация

Боевая модель распознавания строк (`line_int8.onnx`) принимает только **статичный
растр**: маска чернил `[1,1,64,W]` → CNN → `logits [1,T,72]` → CTC. Динамика письма
(скорость пера, нажим, наклон, границы «перо поднято») при растеризации теряется
полностью. Векторные признаки штрихов уже реализованы в `src/ink-features.js`
(пересэмплирование по длине дуги, репер {T,N}, кривизна DTH, log-скорость,
нажим/наклон, pen-up; инвариантность к повороту/сдвигу/масштабу) и экспортируются
в `data/vectors/` (формат `inknet-vectors/1`).

Гипотеза: добавление векторной ветки, обучаемой на той же CTC-разметке, снижает
CER за счёт динамической информации, особенно на неоднозначных курсивных формах.

## 2. Цели / не-цели

Цели:
- Единая модель с двумя входами (растр-полоса + последовательность векторных
  признаков штрихов этой полосы), общий CTC-хед и общий словарь `line_vocab.json`.
- Совместимость с существующим beam-декодером (`src/ctc-decode.js`) и словарным
  бонусом без изменений.
- Fallback: при отсутствии векторного входа (например старый клиент) модель
  должна деградировать gracefully (нулевой/маскированный векторный вход).

Не-цели:
- Замена растра векторами целиком — это отдельный проект `inknet-online.md`.
- Улучшение глиф-MLP (`inknet-mlp/1`) — остаётся инструментом QC/калибровки.

## 3. Архитектура

```
штрихи строки ──► векторная ветка: embed(10-dim feats) → BiLSTM/TCN → F_v [T',d]
                                        ↑ alignment: пулинг по окну полосы
растр-полоса  ──► CNN (существующая)   → F_r [T, d']
F = fuse(F_r, interp(F_v)) → CTC head → logits [1,T,72]
```

- Векторная ветка: лёгкий TCN/BiLSTM поверх признаков stride=10 из
  `buildGlyphVectors`, размер ~0.3–1 М параметров (бюджет int8 — ≤1 МБ сверху).
- Слияние: выравнивание по временной оси полосы (интерполяция F_v по X-координате
  точек штрихов в системе кропа полосы), конкатенация + 1×1 свёртка.
- Вход тензоров: `image [1,1,64,W]` (как сейчас) + `vec [1,M,10]` + `vec_mask`.

## 4. Ключевая инженерная проблема: строки в векторном пространстве

Сейчас `splitLines()` в `src/line-preprocess.js` режет **растр** (горизонтальная
проекция, waist-split). Для векторной ветки нужно то же разбиение, но по
**штрихам**:
- решение: сначала растрируем и делим полосы (без изменений), затем относим
  каждый штрих к полосе по X/Y-покрытию его точек (тот же bbox-критерий, +
  правила разрешения штрихов-«связок» между полосами);
- альтернатива (дороже): полноценный vector splitLines по проекциям полилиний —
  принять на этапе design review.

Оба варианта обязаны давать **идентичную нумерацию полос** на обучении и
инференсе, иначе фичи рассинхронятся.

## 5. Данные и обучение (`../inknet-train`)

- Датасет: расширить экспорт `inknet-collect/1` → `inknet-collect/2` с полями
  `strokes` (сырые точки `{x,y,t,pressure,tiltX,tiltY}`) рядом с текущим
  раст/координатным представлением. Экспорт: `scripts/export-dataset.mjs` +
  `POST /api/train` payload уже содержат штрихи — проверить полноту `t`/нажима.
- Препроцессинг в тренировщике: портировать **точно** `line-preprocess.js`
  (уже сделано для растра) + `ink-features.js` для векторной ветки; parity-тест
  «node vs worker» обязателен (существующая практика репы).
- Оценка: только writer-disjoint CER (leave-one-writer-out), как в
  `build-vector-ds.mjs`. Метрика успеха: CER на held-out авторе ниже базовой
  `line_int8.onnx` ≥ на 5% относительных; покомпонентный ablation (raster-only /
  vector-only / fusion) обязателен.

## 6. Изменения в веб-клиенте

| Файл | Изменение |
|---|---|
| `src/line-preprocess.js` | ассоциация штрихов с полосами; выдача `vec [M,10]` + mask рядом с тензором растра |
| `src/line.worker.js` | второй вход в `session.run` (`vec`, `vec_mask`); ключ `stripCache` расширить хэшем векторов |
| `src/lines.js` | ничего (packStrokes уже шлёт штрихи с pressure/tilt) |
| `.env` / `/api/config` | новый `LINE_MODEL` гибрид; старый остаётся fallback |
| `public/sw.js` | bump `CACHE` при деплое модели (штатная процедура) |
| квантизация | векторные признаки не квантовать в int8 наивным способом — per-channel или отдельный scale; проверить на QC (`model-qc.js` sample-режим) |

## 7. Риски

| Риск | Митигция |
|---|---|
| Векторная ветка не даёт прироста (шум динамических признаков) | ablation до интеграции: vector-only CTC baseline сначала обучить в inknet-train |
| Рассинхрон strip/vector разбиения | фиктивные parity-тесты на всех данных БД (`tests/`) |
| Рост модели и падение int8-точности | бюджет ≤+1 МБ; QC-пайплайн (`model-qc.js`) как gate |
| Мало авторов в датасете | блокиратор: сбор данных через `/collect.html` до старта обучения (см. порог ниже) |

## 8. Этапы

1. **M0 — данные:** ≥8–10 авторов, ≥50 написаний/букву через `collect.html`;
   `make export-vectors` — замерить межавторскую разделимость строчных признаков.
2. **M1 — vector-only CTC baseline** в `inknet-train` (строки, не глифы!) — go/no-go по CER.
3. **M2 — гибрид:** расширение датасета, fuse-архитектура, ablation.
4. **M3 — web-интеграция:** preprocess + worker + cache + sw, e2e (`test-e2e.mjs`).
5. **M4 — деплой:** fp32/int8/`.ort`, QC, bump CACHE, A/B против текущей модели.

## 9. Acceptance criteria

- writer-disjoint CER гибирида < CER текущей `line_int8.onnx` на ≥5% относительных;
- инференс в web не медленнее текущей модели >20% (WebGPU и WASM-путь);
- бит-приближённый parity:worker-preprocess vs тренировщик (тест на корпусе БД);
- graceful fallback при пустом векторном входе (CER не хуже raster-only).
